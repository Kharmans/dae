# DAE v14 Bug Audit — 2026-04-08

Source code scan of `dae-14x/src/module/` for potential bugs and race conditions.

## High Priority

### 1. `evalInline` (async) called from sync hook — `[object Promise]` in change values
- **File:** `dae.ts` (was line 1042-1069)
- **Issue:** `preUpdateActiveEffectEvalInlineHook` was a synchronous `Hooks.on` handler but called `evalInline()` (async). The return value was a Promise object, producing `"[object Promise]"` in change values.
- **Impact:** Any effect with `[[formula]]` inline rolls in change values got garbage values during preUpdate.
- **Fix:** Moved inline eval logic into the async lib-wrapper `_preUpdateActiveEffect` patch, which properly awaits `evalInline()`. Merges `this.system.changes` with `changed.system?.changes` to evaluate the post-update changes. Removed the broken sync hook.
- **Status:** FIXED — test batch 20

## Medium Priority

### 2. `addEffectChange` fire-and-forget async calls — timing unpredictable
- **File:** `dae.ts:1776-1808`
- **Issue:** `addEffectChange` is not async but calls `addConvenientEffectsChange`, `addConditionChange`, `addTokenMagicChange`, and `addCreateItemChange` — all async — without `await`. Callers at lines 911, 1893, and `DAEdnd5e.ts:1492/1503` also don't await.
- **Impact:** Side effects (CE application, status toggling, item creation, token magic) from prepareData-path effect processing complete at unpredictable times.
- **Status:** TODO

### 3. Hook `changeLoop()` / `changesLoop()` not awaited — concurrent effect processing
- **File:** `dae.ts:654, 1037, 1183`
- **Issue:** `createActiveEffectHook`, `updateActiveEffectHook`, and `deleteActiveEffectHook` define inner async functions called without `await`. The hook returns `true` immediately while macro execution, dependent updates, status toggling, and item creation/deletion continue in the background. Rapid hook firing (e.g., bulk effect creation from aura) causes interleaving. `actionQueue` serializes some inner work, but work outside the queue runs concurrently.
- **Impact:** Ordering not guaranteed when multiple effects are created/updated/deleted in quick succession.
- **Status:** TODO — may be intentional design to avoid blocking Foundry hooks

### 4. Live collection modified during iteration in `processConditionalEffects`
- **File:** `dae.ts:2816-2830`
- **Issue:** `for (let effect of actor.effects)` iterates a live `EmbeddedCollection`, then `actor.deleteEmbeddedDocuments("ActiveEffect", ...)` modifies it mid-loop. The `disableCondition` loop (line 2832) using `actor.allApplicableEffects()` generator has the same exposure if `effect.update()` triggers hooks that add/remove effects.
- **Impact:** Effects can be skipped during conditional processing.
- **Status:** TODO

### 5. Cross-scene teleport fire-and-forget with no error handling
- **File:** `daeMacros.ts:123-131`
- **Issue:** `canvasReady` callback calls `socketlibSocket.executeAsGM("createToken")` chained with `.then()` for `deleteToken`. Neither is awaited, no `.catch()`. A failed `createToken` leaves `deleteToken` unexecuted, orphaning the source token.
- **Impact:** Token duplication or loss on failed cross-scene teleport.
- **Status:** TODO

## Low Priority

### 6. Shared `options` object mutated — visible to other modules' hooks
- **File:** `dae.ts:701, 989, 1161`
- **Issue:** Hook `options` object is mutated in place (`options["existing"]`, `options["expiry-reason"]`). Foundry passes the same object to all hooks, so mutations are visible to other modules.
- **Impact:** Unlikely to cause issues in practice, but breaks hook isolation.
- **Status:** TODO

### 7. Init macro effects could be lost if created during drain
- **File:** `dae.ts:97, 2027-2034`
- **Issue:** `pendingInitMacroEffects` is drained in `daeReadyActions` with `length = 0`. An init macro that creates a new effect (pushing to the array) between the loop's last `await` and the clear would lose that entry.
- **Impact:** Unlikely in practice — init macros rarely create effects that themselves need init macros.
- **Status:** TODO

### 8. `finally { return true }` masks all errors
- **File:** Multiple hook handlers
- **Issue:** Pattern ensures hooks never block Foundry operations, but also silently swallows errors. Bugs can hide indefinitely.
- **Impact:** Debugging difficulty, not functional breakage.
- **Status:** Intentional design — document rather than fix

### 9. Failed `effect.update()` aborts remaining effects in loop
- **File:** `specialDurations.ts:134-155`
- **Issue:** `setEffectsExpiryToRounds` iterates effects calling `effect.update()`. If one throws, the loop aborts and remaining effects are not processed.
- **Impact:** One bad effect blocks expiry processing for subsequent effects.
- **Status:** TODO

### 11. `daeMacro` returns after first `macro.execute` change — skips remaining changes
- **File:** `dae.ts:1324`
- **Issue:** The `for` loop over effect changes in `daeMacro` had `return await macro?.execute(scope)` after processing a `macro.execute` or `macro.itemMacro` change. This exited the entire function, skipping any remaining changes on the same effect.
- **Impact:** Effects with multiple macro change keys only worked if `macro.execute`/`macro.itemMacro` was last in the changes array.
- **Fix:** Removed `return` — changed to `await macro?.execute(scope)`. No caller uses `daeMacro`'s return value (all callers are `actionQueue.add(daeMacro, ...)` with no assignment). The loop now continues to process remaining changes.
- **Status:** FIXED — test 19.18
